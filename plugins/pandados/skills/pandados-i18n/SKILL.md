# PandaDOS 国际化

## 核心原则

让产品生成的内容跟随用户语言，同时逐字保留用户和技术材料。英语是源语言与最终回退语言；首发十种 locale 必须保持同一消息键和 ICU 参数契约。

开始改动前，从当前工作目录向上定位 PandaDOS 项目根目录，再阅读根目录下的
`docs/i18n-contributing.zh-CN.md` 和 `shared/i18n/glossary.zh-CN.md`。

## 必须本地化

- 将页面、按钮、标签、空态、加载态、帮助、表单、校验、确认框、Toast、错误和无障碍名称写成语义化消息键；前端通过 `useI18n()`、`t()` 或 `tr()` 展示，不嵌入自然语言字面量。
- 先在英语目录定义语义和参数，再在同一改动中补齐 `en`、`zh-Hans`、`zh-Hant`、`ja`、`ko`、`es`、`fr`、`de`、`pt-BR`、`ru`。遵循当地产品用语，不用英语值或简繁转换占位。
- 将动态数量写成 ICU `plural`/`select`，所有目录保留相同参数名与控制结构；不要拼接数量、单位或半句话。
- 通过共享格式化器和 `Intl` 按 locale/timezone 展示日期、时间、相对时间、数字与列表；不要手写日期顺序、固定时差或“分钟前”等片段。
- 让通知事件只携带稳定事件类型和参数，在每位接收者的发送边界按其 locale/timezone 生成标题、正文、按钮和时间。

## API 错误

- 返回稳定的 `code`、结构化 `params`、英语 `fallback` 和独立的原始 `details`；不要把固定语言的自由文本直接交给界面。
- 在 `shared/i18n/domains/errors.ts` 补齐十种语言消息，并在 `ui/src/lib/api.ts` 将错误码映射到消息键。
- 将 stderr、远端响应和异常文本保留在 `details`，界面使用“本地化说明 + 原始技术详情”，不得翻译诊断内容。

## AI 内容

- 中文 locale 使用中文内部提示词，其他 locale 使用英文内部提示词；始终附加 `outputLanguageInstruction(locale)`，让面向用户的澄清、摘要、审批说明、进度和 reason 使用目标语言。
- 将目标 locale 按发起用户解析；无发起用户时回退项目属主，最后回退 `en`。
- 将自然语言指令与机器协议分开。不得翻译 `NEED_CLARIFY`、`ISSUE_DONE`、`STAGE_DONE`、JSON schema、字段名、枚举、命令或路径。

## 必须保持原文

逐字保留用户提供的 issue 标题与正文、消息、已有聊天记录、代码、命令、文件路径、终端输出、Git 内容，以及 Claude、Codex、tmux、Git 等名称和协议标识。产品生成的默认标题、状态或解释不属于原文，必须本地化或改成稳定技术标识。

## 完成检查

1. 检查新增内容是否在界面、后端错误、通知或 AI 输出中面向用户。
2. 检查十种目录键、ICU 参数、复数结构与术语一致。
3. 检查用户和技术原文没有被翻译、改写或写入固定语言的持久化字段。
4. 运行 `bun run check-i18n`，再运行仓库要求的类型检查、测试和 UI 构建。
